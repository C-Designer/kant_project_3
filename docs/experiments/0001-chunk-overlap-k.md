## 가설·배경

- 무엇이 문제였나: 현재 동결값은 청크 900자, 오버랩 0이다. 쪽이 900자를 넘으면 문장 끝에서 균등하게 나누는데, 나뉜 경계에서 답에 필요한 문장이 두 청크로 갈라질 수 있다. 크기와 오버랩, k를 바꿨을 때 어디서 이득과 손해가 나는지 모른다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나:
  1. 오버랩 10~20%는 경계에 걸린 근거를 살려 같은 크기·k에서 쪽 단위 근거 재현율을 올린다.
  2. 청크가 작을수록(100~300) 한 청크에 담긴 정보가 줄어 같은 k에서 근거 재현율은 떨어지고, k를 키우면 일부 회복된다.
  3. 청크가 클수록 k=6~7에서 입력 문맥이 `CONTEXT_TOKEN_LIMIT`(3,000토큰)에 걸려 뒤 청크가 잘린다(900자 청크 약 480토큰 × 7 > 3,000).
- 좋아졌다고 판단할 기준 (결과를 보기 전에):
  - 기준 조건은 크기 900, 오버랩 0%, k=5이다.
  - 어떤 조합이 기준보다 좋다고 보려면 세 방식 중 두 방식 이상에서 쪽 단위 근거 재현율이 0.05 이상 높고, 행동 일치율(답변·되묻기·보류)이 기준보다 낮지 않아야 한다.
  - 표본이 15문항이라 0.05 미만 차이는 우연으로 본다.

**오버랩 구현**: `src/search/chunking.py`가 겹침을 지원하지 않아(0이 아니면 거부) 스크립트 안에서 구현했다. 쪽이 크기를 넘으면 `_split_body`로 `크기 - 머리줄 - 오버랩`자 이하 조각으로 나눈 뒤, 둘째 조각부터 앞 조각 본문의 마지막 오버랩 글자를 앞에 붙인다. 머리줄(제목·부서·소제목, 40~74자)은 크기에 포함되고 모든 조각 앞에 붙는다. 청크 전체 길이는 항상 크기 이하다. 쪽이 크기 이하면 오버랩 없이 한 쪽 = 한 청크다.

**알려진 한계**: 크기 100에서는 머리줄이 최대 74자라 본문이 26~60자 정도만 남는다(오버랩 20%면 새 글자가 더 줄어든다). 문장 끝 분할이 거의 안 되고 글자 수로 강제 분할되므로, 작은 크기 결과는 "작은 청크의 한계"와 "머리줄이 차지하는 비중"이 섞여 있다.

## 질문 선택·실행 명령

- 질문 목록: `results/questions-2.json` (15문항, 유형 분포 답변/추가 확인/보류 = 9/3/3, 시드 20261105)
- 고른 이유: 기존 팀 비교에 쓴 선택 파일을 그대로 써서 다른 실험과 비교 가능하게 했다. 근거 문서가 없는 되묻기·보류 문항은 검색 지표에서 해당 없음이다.
- 정답·`expected_action`은 답변 생성 뒤 채점에만 썼다: 예 (스크립트는 검색·생성에 질문 문장만 넘긴다)

```bash
uv run python scripts/chunk_overlap_experiment.py retrieve   # 27개 조합 x 3방식, k=7로 검색해 저장
uv run python scripts/chunk_overlap_experiment.py generate   # 조합 x 방식 x k=4~7 답변 생성
uv run python scripts/chunk_overlap_experiment.py report     # 표
```

k=4~6은 k=7 검색 결과의 앞부분이다(세 방식 모두 순위순이라 같은 결과). 답변 생성은 k마다 따로 호출했다.

지표 정의
- Hit@k·Recall@k: 정답 근거 문서(book_id) 기준. 표준 정의(`src/metrics/retrieval_metrics.py`).
- 쪽 단위 근거 재현율: 골든 `evidence_groups` 중 (book_id, 쪽)이 같은 청크가 상위 k에 있는 그룹 비율(그룹 안은 OR). 청크 크기 변화에 book 단위 지표보다 민감해서 함께 본다.
- 행동 일치율: 답변 상태(answered/needs_clarification/abstained)가 `expected_action`(answer/clarify/abstain)과 같은 비율. LLM 채점이 아니라 규칙 비교이며 답변 내용의 정확성은 말해 주지 않는다.
