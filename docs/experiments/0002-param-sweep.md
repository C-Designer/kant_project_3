## 가설·배경

- 무엇이 문제였나 (이전 결과, 실패 사례의 `question_id`): EXP-0001에서 Hit@5는 변별력이 없고(전 실험 1.00), Recall은 질문 구성에 좌우된다. 청킹·`k`·문맥 한도가 검색·답변 품질과 비용(시간·토큰)에 얼마나 민감한지 값을 바꿔 본 적이 없다. 실패 사례 `question_id`는 따로 지정하지 않았다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나:
  1. `chunk_size`를 줄이면 한 청크가 한 사실에 가까워져 Recall은 오르지만 `k`개 문맥에 들어가는 정보량이 줄어 Faithfulness·사실은 내릴 수 있다. 늘리면 반대다.
  2. `overlap`을 두면 경계에 걸친 근거를 덜 놓쳐 Recall이 오르지만 같은 내용이 중복돼 입력 토큰이 는다.
  3. `topK`를 키우면 Recall은 오르고 입력 토큰·응답 시간도 는다. 줄이면 반대다.
  4. `context_size`(문맥 토큰 한도)는 기준(3000)에서 이미 안 잘린다(실측 최대 1,857). **낮출 때만** 문맥이 잘려 품질이 떨어질 것이고, 올려도 변화가 없을 것이다.
  5. 리랭커 후보 수는 EXP-0001(E3→E4)에서 50→20이 품질 변화 없이 시간을 줄였다. 10까지 줄여도 같은지 본다.
- 좋아졌다고 판단할 기준 (결과를 보기 **전에** 적는다. 아래는 초안이며 리드 확인 후 확정한다):
  - **검색 지표(Hit@k·Recall@k)는 같은 색인·질문이면 결정적**이다. 기준 설정 대비 Recall이 0.05 이상 달라지면 효과가 있다고 본다.
  - **Faithfulness·시간은 잡음이 있다.** 기준 설정을 3번 반복해 얻은 범위(최소~최대)를 잡음 폭으로 두고, 그 폭 밖으로 벗어난 차이만 효과로 본다. 폭 안의 차이는 "차이 없음"으로 적는다.
  - **비용:** 검색 단계 시간이 기준 대비 20% 이상, 입력 토큰이 10% 이상 달라지면 의미 있는 변화로 본다.
  - 조건·근거·판단(Judge)은 이번 실험의 측정 대상이 아니다. 사실·조건·근거·판단 점수는 만들지 않는다.

**Docker는 Linux VM이라 호스트 GPU(MPS)를 못 쓴다.** 로컬에서 잰 값(20쌍 리랭크): MPS **0.33초**, CPU 3스레드 **2.65초**(약 8배). 이 측정은 청크 약 350자 가짜 문장이라 실제 900자 청크는 더 느릴 수 있다. 따라서:

- 컨테이너에서 잰 `hybrid_rerank` 응답 시간은 **호스트 실행(EXP-0001, 지난 비교표)의 절대값과 비교하지 않는다.** 설정 사이의 상대 차이만 본다.
- 기준 설정은 같은 컨테이너 환경에서 다시 돌려 기준으로 삼는다(호스트 결과를 기준으로 쓰지 않는다).
- 컨테이너에서 실측: 20쌍 리랭크 **12.1초**(호스트 CPU 3스레드 2.65초, MPS 0.33초), 프로세스 최대 메모리 **2.8GB**. 그래서 한도를 4GB로 정했다.
- 기준 설정의 Recall은 호스트 실행과 같다(naive 0.67 / hybrid 0.74 / hybrid_rerank 0.70). 컨테이너에서 새로 만든 색인(청크 572개)이 호스트 색인과 같은 수준의 검색을 한다는 간접 확인이다(청크 수·검색 결과 자체를 호스트와 대조하지는 않았다).

### latency 측정 (2026-11-12 확정)

병렬 실행에서는 로컬 연산(CPU·메모리 대역폭)과 LLM API 호출(동시 요청 대기·한도)이 서로 간섭해 응답 시간이 흔들린다. 그래서 둘로 나눠 잰다.

1. **검색 단계 시간:** LLM 없이 질문 15개 × 방식 × 설정을 따로 돌려 잰다(비용 없음). 설정 간 비교는 이 값의 중앙값으로 한다. 기준·변수 13개는 질문당 3회 반복의 중앙값, 1단계 탐색은 1회.
2. **생성 시간·전체 응답 시간:** 병렬 실행에서 나온 값. 참고용이며 출력 토큰 수와 함께 본다(생성 시간은 대체로 출력 토큰에 비례).

**기준 3회로 본 잡음 폭**: Recall·문맥 토큰·입력 토큰은 세 번 모두 같다(결정적). Faithfulness는 방식마다 0.03~0.04 폭, 응답 시간은 ±0.4초, 판단 일치는 0.67~0.73이다. 아래에서 Recall은 기준 ±0.05, Faithfulness는 이 폭, 검색 시간은 ±20%, 입력 토큰은 ±10%를 효과의 기준으로 썼다(위 "좋아졌다고 판단할 기준" 초안).

- **topK:** 키우면 Recall이 오른다(naive +0.07, hybrid_rerank +0.06, hybrid는 +0.01). 줄이면 모든 방식에서 내린다(−0.07~−0.14). Faithfulness도 같은 방향이다(topK 3에서 naive −0.08, hybrid −0.10은 폭 밖). 대가는 입력 토큰(topK 8에서 +41%, topK 3에서 −28%)이고 응답 시간은 거의 안 바뀐다. 5~8 사이 어디가 효율적인지는 값이 2개뿐이라 알 수 없다.
- **chunk_size 600:** 방식에 따라 반대다. naive는 Recall −0.13·Faithfulness −0.08, hybrid는 Recall −0.06, **hybrid_rerank는 Recall −0.01이면서 Faithfulness +0.06, 입력 토큰 −20%, 검색 시간 −25%**. 작은 청크는 리랭커가 있을 때만 이득으로 보인다. chunk 1200은 해석 보류.
- **overlap:** 효과를 못 찾았다. Recall 변화는 ±0.02, 입력 토큰은 0~6% 증가, Faithfulness는 방식마다 부호가 엇갈린다(우연으로 본다). 청킹 교체가 실제로 적용됐는지는 색인을 직접 열어 확인했다(두 overlap 색인 모두 청크 212개의 텍스트가 기준과 다르고 인접 청크 212쌍이 지정 글자 수만큼 정확히 겹침).

Recall은 잘림 전 검색 결과로 재므로 변하지 않는다. 가설 4(올려도 변화 없음)는 topK 5에서만 맞고, topK 8은 문맥이 최대 약 3,000토큰(실측 2,944~2,992)이라 한도 3,000에 붙어 있다.
