- 날짜: 2026-11-12~13
- 작성자: @C-Designer
- run_id: 설정 라벨 `baseline-r1·r2·r3`, `topk-3`, `topk-8`, `chunk-600`, `chunk-1200`, `overlap-100`, `overlap-200`, `ctx-1000`, `ctx-1500`, `rerank-10`, `rerank-50`. Langfuse run 이름은 `<MMDD-HHMM>-<방식>-<라벨>`(프로젝트 `kant-exp-stone`, 데이터셋 `kant-exp-basic15`). 점검용 `smoke`와 호스트에서 돌린 `1111-…` run은 비교에서 제외

## 가설·배경

- 무엇이 문제였나 (이전 결과, 실패 사례의 `question_id`): EXP-0001에서 Hit@5는 변별력이 없고(전 실험 1.00), Recall은 질문 구성에 좌우된다. 청킹·`k`·문맥 한도가 검색·답변 품질과 비용(시간·토큰)에 얼마나 민감한지 값을 바꿔 본 적이 없다. 실패 사례 `question_id`는 따로 지정하지 않았다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나:
  1. `chunk_size`를 줄이면 한 청크가 한 사실에 가까워져 Recall은 오르지만 `k`개 문맥에 들어가는 정보량이 줄어 Faithfulness·사실은 내릴 수 있다. 늘리면 반대다.
  2. `overlap`을 두면 경계에 걸친 근거를 덜 놓쳐 Recall이 오르지만 같은 내용이 중복돼 입력 토큰이 는다.
  3. `topK`를 키우면 Recall은 오르고 입력 토큰·응답 시간도 는다. 줄이면 반대다.
  4. `context_size`(문맥 토큰 한도)는 기준(3000)에서 이미 안 잘린다(실측 최대 1,857). **낮출 때만** 문맥이 잘려 품질이 떨어질 것이고, 올려도 변화가 없을 것이다.
  5. 리랭커 후보 수는 EXP-0001(E3→E4)에서 50→20이 품질 변화 없이 시간을 줄였다. 10까지 줄여도 같은지 본다.
- 좋아졌다고 판단할 기준 (결과를 보기 **전에** 적는다. 아래는 초안이며 리드 확인 후 확정한다):
  - **검색 지표(Hit@k·Recall@k)는 같은 색인·질문이면 결정적**이다. 기준 설정 대비 Recall이 0.05 이상 달라지면 효과가 있다고 본다.
  - **Faithfulness·시간은 잡음이 있다.** 기준 설정을 3번 반복해 얻은 범위(최소~최대)를 잡음 폭으로 두고, 그 폭 밖으로 벗어난 차이만 효과로 본다. 폭 안의 차이는 "차이 없음"으로 적는다.
  - **비용:** 검색 단계 시간이 기준 대비 20% 이상, 입력 토큰이 10% 이상 달라지면 의미 있는 변화로 본다.
  - 조건·근거·판단(Judge)은 이번 실험의 측정 대상이 아니다. 사실·조건·근거·판단 점수는 만들지 않는다.

## 실험 환경·자원 제한

설정끼리 서로 영향을 주지 않게 독립된 컨테이너에서 돌린다. 모든 설정이 **같은 이미지·같은 한도·같은 파이프라인**(컨테이너 안에서 새 색인 → LLM 없는 검색 지표 → Langfuse 실험)을 거친다.

| 항목 | 값 | 상태 |
|---|---|---|
| 호스트 | Apple M5 Max, 18코어, 64GB | 확인 |
| 격리 단위 | Docker 컨테이너 하나가 설정 하나. CPU·메모리 제한을 둔다 | 확정 |
| 병렬도 | **실제로는 순차 1개.** 5개(변수당 1개)로 정했지만 Docker VM이 7.7GB이고 팀 공용 Langfuse·ClickHouse·Qdrant 컨테이너가 같은 VM에서 약 2.5GB를 쓴다. 실험 컨테이너는 하나가 최대 2.8GB라 2개를 동시에 띄우면 VM 메모리를 넘겨 공용 서비스가 OOM으로 죽을 수 있다 | 변경 (2026-11-12) |
| 컨테이너당 자원 | `--cpus=3 --memory=4g --memory-swap=4g`, `OMP_NUM_THREADS=3`·`MKL_NUM_THREADS=3` | 확정 (실측 최대 2.8GB) |
| Docker Desktop VM | **7.7GB 그대로.** 병렬(3개)로 돌리려면 16GB 이상으로 올려야 하고, 올리면 공용 서비스가 잠시 내려간다(사용자가 직접 설정) | 미변경 |
| LLM 동시 호출 | 컨테이너 하나에서 질문 3개 동시(`max_concurrency=3`) | 확정 |
| Faithfulness 채점 | 전 설정 3회(`FAITHFULNESS_REPEATS=3`) | 확정 |
| 색인 | 컨테이너 안에서 설정마다 새로 색인한다(`EXP_INDEX_DIR`, 로컬 Qdrant 폴더). 로컬 Qdrant는 폴더 하나에 프로세스 하나만 열 수 있다. HF 모델 캐시는 읽기 전용 마운트 + `HF_HUB_OFFLINE=1`이라 모든 설정이 같은 가중치를 쓴다 | 확정 |
| Langfuse | 실험 전용 프로젝트 `kant-exp-stone`(팀원 `shipping-rag`와 분리, 스크립트가 프로젝트 이름을 확인하고 다르면 중단). `LANGFUSE_TIMEOUT=60`, `TRACE_USER=stone-exp`. 데이터셋 `kant-exp-basic15`, run 이름 `<MMDD-HHMM>-<방식>-<라벨>` | 확정 |

**Docker는 Linux VM이라 호스트 GPU(MPS)를 못 쓴다.** 로컬에서 잰 값(20쌍 리랭크): MPS **0.33초**, CPU 3스레드 **2.65초**(약 8배). 이 측정은 청크 약 350자 가짜 문장이라 실제 900자 청크는 더 느릴 수 있다. 따라서:

- 컨테이너에서 잰 `hybrid_rerank` 응답 시간은 **호스트 실행(EXP-0001, 지난 비교표)의 절대값과 비교하지 않는다.** 설정 사이의 상대 차이만 본다.
- 기준 설정은 같은 컨테이너 환경에서 다시 돌려 기준으로 삼는다(호스트 결과를 기준으로 쓰지 않는다).
- 컨테이너에서 실측: 20쌍 리랭크 **12.1초**(호스트 CPU 3스레드 2.65초, MPS 0.33초), 프로세스 최대 메모리 **2.8GB**. 그래서 한도를 4GB로 정했다.
- 기준 설정의 Recall은 호스트 실행과 같다(naive 0.67 / hybrid 0.74 / hybrid_rerank 0.70). 컨테이너에서 새로 만든 색인(청크 572개)이 호스트 색인과 같은 수준의 검색을 한다는 간접 확인이다(청크 수·검색 결과 자체를 호스트와 대조하지는 않았다).

### latency 측정 (2026-11-12 확정)

병렬 실행에서는 로컬 연산(CPU·메모리 대역폭)과 LLM API 호출(동시 요청 대기·한도)이 서로 간섭해 응답 시간이 흔들린다. 그래서 둘로 나눠 잰다.

1. **검색 단계 시간:** LLM 없이 질문 15개 × 방식 × 설정을 따로 돌려 잰다(비용 없음). 설정 간 비교는 이 값의 중앙값으로 한다. 기준·변수 13개는 질문당 3회 반복의 중앙값, 1단계 탐색은 1회.
2. **생성 시간·전체 응답 시간:** 병렬 실행에서 나온 값. 참고용이며 출력 토큰 수와 함께 본다(생성 시간은 대체로 출력 토큰에 비례).

## 구현 작업 분담 (Codex)

|---|---|---|---|
| T1 | `exp/exp2-inject` | gpt-6-luna / medium | `scripts/exp_config.py`, `scripts/lf_experiment.py`(`--no-judge`, 설정 라벨, CSV) |

## 해석·한계

**기준 3회로 본 잡음 폭**: Recall·문맥 토큰·입력 토큰은 세 번 모두 같다(결정적). Faithfulness는 방식마다 0.03~0.04 폭, 응답 시간은 ±0.4초, 판단 일치는 0.67~0.73이다. 아래에서 Recall은 기준 ±0.05, Faithfulness는 이 폭, 검색 시간은 ±20%, 입력 토큰은 ±10%를 효과의 기준으로 썼다(위 "좋아졌다고 판단할 기준" 초안).

- **topK:** 키우면 Recall이 오른다(naive +0.07, hybrid_rerank +0.06, hybrid는 +0.01). 줄이면 모든 방식에서 내린다(−0.07~−0.14). Faithfulness도 같은 방향이다(topK 3에서 naive −0.08, hybrid −0.10은 폭 밖). 대가는 입력 토큰(topK 8에서 +41%, topK 3에서 −28%)이고 응답 시간은 거의 안 바뀐다. 5~8 사이 어디가 효율적인지는 값이 2개뿐이라 알 수 없다.
- **chunk_size 600:** 방식에 따라 반대다. naive는 Recall −0.13·Faithfulness −0.08, hybrid는 Recall −0.06, **hybrid_rerank는 Recall −0.01이면서 Faithfulness +0.06, 입력 토큰 −20%, 검색 시간 −25%**. 작은 청크는 리랭커가 있을 때만 이득으로 보인다. chunk 1200은 해석 보류.
- **overlap:** 효과를 못 찾았다. Recall 변화는 ±0.02, 입력 토큰은 0~6% 증가, Faithfulness는 방식마다 부호가 엇갈린다(우연으로 본다). 청킹 교체가 실제로 적용됐는지는 색인을 직접 열어 확인했다(두 overlap 색인 모두 청크 212개의 텍스트가 기준과 다르고 인접 청크 212쌍이 지정 글자 수만큼 정확히 겹침).
- **context_size(topK 5):** 1000이면 15문항이 모두 잘리고(1500은 8~14문항), naive·hybrid의 Faithfulness가 최대 0.08 내렸다. **hybrid_rerank는 변화가 없었다.** 리랭커가 좋은 청크를 앞에 놓아 뒤가 잘려도 영향이 적은 것으로 짐작하나 검증하지 않았다. Recall은 잘림 전 검색 결과로 재므로 변하지 않는다. 가설 4(올려도 변화 없음)는 topK 5에서만 맞고, topK 8은 문맥이 최대 약 3,000토큰(실측 2,944~2,992)이라 한도 3,000에 붙어 있다.
- **리랭커 후보 수:** 10은 Recall을 잃지 않고(+0.01) 검색 시간이 절반(−47%), 50은 Recall 이득 없이 41% 느려진다. 후보는 dense 20 + keyword 20의 합집합이라 최대 40이고 50은 40과 같다. 판단 일치는 10에서 0.60으로 낮았다(질문 3개 차이).

**말해주지 못하는 것**: 15문항이라 한 문항이 6.7%p다. Faithfulness 잡음 폭은 반복 3회로 잰 값이라 실제보다 좁을 수 있다(±0.03 안팎의 차이는 구분하지 못한다). 변수 값이 2개뿐이라 **각 변수의 최적점은 아직 못 찾았다.** 변수를 하나씩만 바꿨으므로 변수 사이 상호작용(topK × 문맥 한도 × 청크 크기)은 보이지 않는다. `action_match`는 기준 설정에서도 0.67~0.73에 머물러 변수 효과를 읽는 용도로 쓰지 않았다. 호스트 실행(11/11)에서 질문별로 보니 같은 5개 질문이 세 방식 모두에서 기대 동작과 달랐다(`abstain` 기대인데 `answered` 3개, `clarify` 기대인데 `abstained` 2개, 답변 내용은 대체로 타당). 이번 컨테이너 실행에서 질문별로 다시 확인하지는 않았다. 조건·근거·판단 Judge 점수는 만들지 않았다.

**조건이 달랐던 점이 결과에 준 영향**: 컨테이너(CPU 전용)와 호스트(MPS)의 속도 차이로 `hybrid_rerank` 응답 시간이 호스트 실행(EXP-0001 E3의 중앙값 6.2초)보다 크게 느리다(기준 평균 약 24초, 평균과 중앙값이라 정확한 배수는 말하지 않는다). 설정 사이의 상대 비교만 유효하다.

## 2단계 탐색 계획 (2026-11-12 결정)

변수당 값이 2개뿐이라 최적점을 못 찾았다. 값을 늘려(격자) 두 단계로 찾는다.

1. **1단계(검색 지표만, LLM 없음):** 아래 격자 전체를 새 색인으로 돌려 Hit/Recall, 문맥 토큰, 잘림, 검색 시간을 잰다. 라벨 `s1-<변수>-<값>`, 검색 시간은 반복 1회. 설정당 약 10분.
2. **2단계(LLM 평가):** 변수마다 **상위 3개** 값만 **세 방식 전부**로 Faithfulness까지 평가한다(전 설정 3회, `--no-judge`). 컨테이너 **4개 병렬**(Docker VM 20GB, 컨테이너당 CPU 3·메모리 4GB, 컨테이너 안 새 색인 + LLM 단계만; 검색 지표는 1단계 값을 쓴다). 이미 LLM 평가가 끝난 값(13개 설정)은 다시 돌리지 않는다.
   **선택 규칙(1단계 결과를 보기 전에 정해 둔다, 2026-11-13).** 선택에는 `hybrid_rerank`의 검색 지표만 쓴다(최종 후보에 가장 가깝고 LLM 없이 잴 수 있다. 다른 방식의 최적값이 다를 수 있다는 한계는 해석에 적는다).
   - `topK`·`chunk_size`·`overlap`·리랭커 후보 수: Recall이 그 변수 안 최고값에서 **0.02 이내**인 값 중 **문맥 토큰 평균이 적은 순**(같으면 검색 시간이 짧은 순)으로 3개. 기준값도 후보에 포함해 순위를 매긴다(기준이 3위 안에 못 들어도 비교용으로 이미 돌렸다).
   - `context_size`(topK 8에서): Recall은 잘림 전 검색 결과로 재므로 값을 바꿔도 변하지 않아 위 규칙을 쓸 수 없다. 대신 **잘림이 시작되는 지점**을 본다: 1단계의 `hybrid_rerank` 잘린 질문 수가 0이 되는 가장 작은 값(손실 없는 최소 한도)과, 그보다 작은 값 중 잘린 질문 수가 가장 적은 2개를 뽑는다.
   - 위 규칙을 결과를 본 뒤에 바꾸면 그 사실과 이유를 이 문서에 적는다.
   - **규칙 보완(2026-11-13, 1단계 일부 결과를 본 뒤):** Recall이 결정적이고 값 간격이 작아 "최고값에서 0.02 이내"에 든 값이 `topK`·`chunk_size`에서 1개뿐이었다(1단계 진행 중 시험 실행에서 확인). 3개를 채우려고 band 안 값이 3개 미만이면 **Recall이 높은 순으로 남은 값을 채운다**(band 안의 정렬은 그대로 문맥 토큰 적은 순). 변경 전 규칙의 결과와 비교하려면 `scripts/exp_pick_candidates.py`의 `RECALL_BAND` 앞 구간을 보면 된다.
