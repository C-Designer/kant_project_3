- 상태: 완료
- 날짜: 2026-11-11
- 작성자: @yshzjq
- run_id: 없음 (탐색용 분석 스크립트로 측정, 공식 metrics run이 아님)
- 관련: EXP-0002(청킹), EXP-0005(k와 3000토큰 한도), EXP-0011(토큰 상한 × k 격자), spec `docs/specs/search.md`, 스크립트 `search-notes/subsel_ia/budget_grid_overlap.py`·`overlap_detail.py`·`overlap_aggregate.py`·`ragas_four.py`(저장소 밖 로컬)

> 이 문서의 값은 `metrics`의 RunRecord·`judge`의 EvalRecord 흐름이 아니라 분석 스크립트로 잰 **탐색용 값**이다. 팀 비교표에 쓰는 값이 아니다. 답변 생성은 프로젝트의 `answer.chain.generate()`를 그대로 불렀지만 채점(RAGAS)은 아래 근사 조건으로 했다.

## 가설·배경

- 무엇이 문제였나: EXP-0011·EXP-0013 격자에서 청크 크기와 k를 바꿀 때 Recall과 충분 판정이 어떻게 달라지는지 봤지만, 오버랩(겹침)은 현재 저장소 청킹이 지원하지 않아(0이 아니면 `ValueError`) 이 격자에 없었다. 또 검색 지표만 봤고 실제 LLM 답변의 행동 일치, 품질(RAGAS), 토큰·시간은 재지 않았다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나: 청크 크기와 k를 바꾸고 오버랩을 넣으면 청크 경계에서 잘리는 근거가 줄어 Recall과 쪽+인용문이 오를 것이다(사용자 가설).
- 좋아졌다고 판단할 기준: 사전 기준 없음(사후 정리). 56문항 Recall은 한 문항이 약 .018, 60문항 행동 일치율은 한 문항이 약 .017이라 그 안쪽 차이는 구별하지 않는다.

## 해석·한계

- 결과가 말해주는 것:
  1. **오버랩은 이득이 없다.** 오버랩 0%에서 10%·20%로 바꿔도 크기 100~800·k 8~11 평균 Recall이 hybrid는 .750 → .746·.736, hybrid_rerank는 .754 → .757·.745로 .02 안쪽이고, naive만 .678 → .701(10%)·.686(20%)로 높다. 쪽+인용문은 hybrid(.266 → .256·.244)와 hybrid_rerank(.320 → .302·.299)에서 오히려 낮아지는 쪽이다. 청크가 길어져 3000토큰에 들어가는 개수가 줄어든 것이 한 원인일 수 있으나 확인하지 않았다.
  2. **청크 크기 효과는 방식마다 다르다.** k=10 Recall(오버랩 평균)은 naive가 100자 .629에서 900자 .761로 큰 청크일수록 높고, hybrid는 .717~.776으로 완만하며(800자 .776), hybrid_rerank는 400~800자에서 .776~.802로 높고(800자 최고) 100자 .695와 300자 .738이 낮다. 방식별 Recall 최고 설정은 naive 600자·오버랩 10%·k=11(.771), hybrid 800자·오버랩 0%·k=11(.817), hybrid_rerank 800자·오버랩 10%·k=10(.824, k=11도 .824)이다. 쪽+인용문 최고는 hybrid_rerank 800자·오버랩 0%(.536).
  3. **답변 행동 일치율은 설정 사이 차이가 작다.** 312개 설정 평균 .914(범위 .817~.967)이고, 100자 청크에서 가장 낮다(k=10에서 naive .861, hybrid .867, hybrid_rerank .900). 한 문항이 .017이라 .03 안쪽 차이는 노이즈일 수 있다. 근거 문서 인용률은 평균 .922이다.
  4. **RAGAS는 세 방식 최고 설정에서 비슷하다.** faithfulness .899~.941, answer relevancy .746~.793, context precision .931~.970, context recall .909~.929. context precision은 hybrid_rerank(.970)가 가장 높고 faithfulness는 naive(.941)가 가장 높지만 모두 60문항 평균의 차이가 .05 안쪽이다.
  5. **토큰·시간은 청크 크기에 따라 늘어난다.** hybrid_rerank k=10에서 입력 토큰은 100자 1,389에서 800자 3,949로 늘고 출력은 약 340~420(100자만 579)이다. 검색 시간은 100자 0.254초에서 800자 0.798초(900자 오버랩 10% 0.898초)로 늘어난다. 답변 LLM 시간은 4.3~6.9초이고 100자(6.86초)가 가장 길다(원인 미확인).
- 말해주지 못하는 것: 56~60문항이라 Recall .02, 행동 일치율 .03 안쪽 차이는 우연일 수 있다. 같은 질문에 반복 실행(검색은 결정적이지만 LLM 답변·RAGAS는 흔들림)하지 않았고, 312개 설정 중 가장 높은 값을 골랐으므로 최고값은 실제보다 높을 수 있다. 확정값(900자·오버랩 0)을 격자에서 뺐으므로 "확정값 대비" 개선 폭은 이 문서만으로 말할 수 없다(EXP-0013·EXP-0011의 확정값 값과 대조해야 한다). 충분/부분/불충분 판정은 이번에 하지 않았다.
- 조건이 달랐던 점이 결과에 준 영향: (1) 오버랩은 저장소가 지원하지 않아 스크립트 구현이다. 저장소 구현이 생기면 방식이 다를 수 있다. (2) 청크 크기 900·오버랩 0은 격자에 없다(900자는 오버랩 10%·20%만 있어 오버랩 평균에서 900자는 제외). (3) hybrid_rerank의 리랭크 후보를 22개로 고정했다. (4) RAGAS의 reference는 `required_facts`를 이은 글이라 정의와 다르다(아래). (5) 답변 LLM 시간은 24개 병렬 호출 중 측정했다.
- RAGAS 근사: 골든 데이터셋에 정답 문장이 없어 context precision·recall의 reference를 `required_facts`로 대신했고, 보류·되묻기 문항의 `required_facts`는 보류·되묻기의 근거라서 이 두 지표의 의미가 답변 문항과 다르다. answer relevancy는 LLM이 요청한 3개 대신 1개만 반환해(래퍼 한계) 생성 질문 1개로 계산했다. faithfulness는 프로젝트 judge와 같은 보류 문장 빼기를 썼지만 1회만 채점했다(프로젝트는 `FAITHFULNESS_REPEATS` 3회 평균).
- 방식 간 차이가 실험 효과인지 우연인지 확인한 방법: 없음. 같은 60문항을 한 번씩 돌렸고, (크기, k) 32개 조합에서 오버랩 10%·20%가 0%보다 높은 조합 수(위 표)로 방향의 일관성만 봤다.

- 첫 답변 수집 실행은 토큰·LLM 시간 기록이 없어(한 설정이 끝난 시점에) 중단하고 기록을 추가해 처음부터 다시 돌렸다. 중단한 실행의 결과(`100_0.json` 하나)는 지우고 쓰지 않았다.
- 답변 수집을 한 번 더 중단했다가(500자 오버랩 20% 설정은 끝나기 전이라 저장되지 않음) 같은 스크립트로 이어서 마저 돌렸다. 설정마다 파일을 따로 저장하므로 이미 끝난 14개 설정은 다시 하지 않았다.
- 답변 호출 오류 9건(전체 18,720개 레코드): 100자 오버랩 10% hybrid k=9, 200자 0% naive k=11, 200자 20% hybrid_rerank k=8, 400자 20% hybrid_rerank k=10, 700자 20% hybrid_rerank k=11, 800자 0% hybrid_rerank k=10·k=11, 800자 20% hybrid_rerank k=8, 900자 20% naive k=8. 오류 사유는 8건이 `ValidationFailed: 출력 형식 오류`(모델 출력의 JSON 파싱 실패, `REGENERATE_MAX` 1회 재생성 후)이고 1건이 `LLMError: model_timeout`이며 레코드의 `error`에 있다. 지표(행동 일치율, 토큰)에서 제외했다. 재시도 단계는 두지 않았다.
- RAGAS faithfulness 값 없음 2건(naive 설정 1건, hybrid 설정 1건): RAGAS가 NaN을 반환했다(사실 주장 없음). 오류는 0건.
- **naive 검색 시간(오버랩 0% 설정)의 평균이 부풀려져 있다.** 크기마다 첫 방식인 naive의 첫 질문 1건에 질문 임베딩 모델 로딩 시간(약 3.7~4.5초)이 섞였다(예: 100자 오버랩 0%의 첫 질문 3.99초, 이후 0.02초). 그 결과 오버랩 0% 설정의 naive 평균이 0.077~0.088초이고 10%·20% 설정은 0.007~0.020초이다. 중앙값(0.007~0.022초)을 봐야 하며 hybrid·hybrid_rerank 시간에는 영향이 없다(이미 로딩된 뒤). 이 시간은 `budget_grid_overlap.py`가 잰 값이고, 답변 수집 스크립트(`overlap_detail.py`)는 설정마다 먼저 한 번 검색해 로딩을 뺐으나 보고서의 검색 시간은 앞의 값을 썼다.
- RAGAS answer relevancy 계산 중 `LLM returned 1 generations instead of requested 3` 경고가 반복됐다(래퍼가 n=1만 반환). 위 근사 항목에 적었다.
- 검색 격자 첫 시도 중 `CUDA error: unknown error`가 한 번 났고(EXP-0013), 이 격자는 GPU 정상 확인 뒤 오류 없이 끝났다. 자동 채점 오류를 사람이 고친 경우, 검색 실패로 기록한 보류 문항, 모의 오류·`--mock` 제외: 없음.
