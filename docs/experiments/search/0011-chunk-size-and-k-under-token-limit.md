# EXP-0011. 3000토큰 한도 안에서 청크 크기와 k를 함께 바꿔 naive·hybrid·hybrid_rerank를 비교한다

- 상태: 완료
- 날짜: 2026-11-11
- 작성자: @yshzjq
- run_id: 없음 (탐색용 분석 스크립트로 측정, 공식 metrics run이 아님)
- 관련: EXP-0002(청크 크기), EXP-0005(k와 3000토큰 한도), EXP-0009(`hybrid_rerank_subq`), spec `docs/specs/search.md`, 스크립트 `search-notes/subsel_ia/budget_*.py`, `grid_basic_*`(저장소 밖 로컬)

> 이 문서의 모든 측정은 `retrieve.retrieve()`를 직접 불러 분석 스크립트 안에서 계산한 탐색용 값이다. `metrics`의 RunRecord와 `judge`의 EvalRecord를 거치지 않았으므로 팀 비교표 값이 아니다. 설정을 바꾸기로 하면 공식 흐름으로 다시 잰다.

## 가설·배경

- 무엇이 문제였나: 확정값(청크 900자, k=5)은 k개 토큰 합이 평균 1,523(naive)~1,549(hybrid)라 한도 3000의 절반만 쓴다(Basic 평균 청크 299토큰).
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나: 청크를 작게 하고 k를 키워 3000토큰에 가깝게 채우면 "답할 재료가 충분한가"(gpt-6-luna 판정)와 Recall이 오를 것이다.
- 좋아졌다고 판단할 기준: 사전 기준 없음(사후 정리). 판정은 LLM 1회라 ±1~2문항을 노이즈로 본다.

## 예시

예시 문항은 [README의 S-DEV-08](README.md#예시-문항-s-dev-08)이다. 같은 문항을 hybrid_rerank로 세 가지 설정에서 돌린 결과다(골든 quote가 적힌 쪽은 SB05 3쪽, SB10 3쪽, SB06 1쪽).

| 설정 | 청크 수 | 담긴 청크 · 토큰 합 | 들어온 문서 | 골든 quote를 담은 청크 |
|---|---|---|---|---|
| 900자 / k=5 | 572 | 5개 · 1,917 | SB05, SB06, SB12, SB15 | SB05 3쪽만 (`SB05-p3-c1`) |
| 772자(400토큰) / k=10 | 658 | 10개 · 2,981 | SB05, SB06, SB10, SB12, SB14, SB15 | SB05 3쪽만 |
| 386자(200토큰) / k=18 | 1,160 | 18개 · 2,788 | SB05, SB10, SB12, SB14, SB15 | SB10 3쪽만 (`SB10-p3-c2`) |

772자에서는 SB10 문서가 들어와 문서 단위 Recall은 오르지만, 골든 쪽(SB10 3쪽)의 청크가 아니라서 쪽+인용문은 그대로다. 386자에서는 SB10 3쪽의 근거는 잡히지만 SB05 3쪽의 근거를 담은 청크는 18개 안에 들어오지 못했다. 세 설정 모두 SB06 1쪽의 근거는 담지 못했다.

## 비교 조건

| 구분 | 값 |
|---|---|
| 바꾼 것 (기준 → 실험) | 청크 크기와 k를 함께: 토큰 상한(글자 = 토큰 × 1.93) 100~600과 k 5~30, 그다음 글자 상한 100~900 × k 8~11 격자 |
| 비교 대상 방식 | naive / hybrid / hybrid_rerank. `hybrid_rerank_subq`는 지연 때문에 이번 비교에서 제외(사용자 결정) |
| 동결 확인 | 다른 것: `config.CHUNK_SIZE` 900, k 5(동결값)를 실험에서 바꿈. 3000토큰 한도(`CONTEXT_TOKEN_LIMIT`)와 모델은 같음 |
| 기록할 것 | hybrid: E5·BM25 각 `max(20, k)`개를 RRF 60. hybrid_rerank: 후보 `max(20, 2k)`개(큰 격자는 22개 고정), `bge-reranker-v2-m3`. 판정 gpt-6-luna, 60문항(Basic=개발용+additional, Intermediate·Advanced도 각 60) |
| 색인 | 로컬 메모리 Qdrant(`QDRANT_URL` 비움), GPU(임시 CUDA torch) |
| 코드 상태 | 저장소 코드 불변. config 값만 스크립트 안에서 메모리로 변경. `git_commit`/`git_dirty` 기록 없음 |

- 지표는 모두 "실제 답변에 들어가는" 목록 기준이다. 3000토큰을 넘으면 뒤 청크를 버린 앞부분(`build_context`)으로 계산한다. Intermediate는 표 청크 상한을 1100/900 비율로 줄였고, Advanced는 본문 상한만 바꿨다(확정 BM25 번호 통째).
- 정답·근거는 선정에 쓰지 않았고 채점에만 썼다.

## 해석·한계

- 결과가 말해주는 것: (1) 3000토큰에 가깝게 채운 조합에서 충분이 확정값보다 오르는 경향이 Basic의 세 방식에서 보인다(표 전체 범위: hybrid 44~51, naive 41~51, hybrid_rerank 45~51. 확정값은 각각 45, 37, 46이고 100토큰/k=30은 세 방식 모두 확정값과 같거나 낮다). Advanced hybrid_rerank 400토큰/k=10은 36에서 35로 오히려 1 낮다. (2) 효과는 hybrid_rerank에서 가장 작다(Intermediate +2, Basic은 100/30을 뺀 조합에서 +1~5). (3) 큰 격자에서 k를 같게 하면 청크가 작아도 Recall이 오르지 않는다. naive는 큰 청크일수록 높고(100자 .625 → 900자 .769), hybrid_rerank는 500자에서 가장 높았다(k=10 Recall은 200자 .780, 400자 .784, 500자 .808, 800자 .796, 900자 .792로 사실상 평평해 차이는 노이즈 범위일 수 있다). 앞의 "작은 청크가 낫다"는 결과는 작은 청크 덕이 아니라 같은 토큰 한도에 더 많은 청크를 넣은 효과일 가능성이 크다(확인한 것은 아님).
- 쪽+인용문(근거 쪽까지 맞히는 지표)은 작은 청크에서 오르지 않는다. 100자는 사실상 0.018이고, hybrid_rerank는 800~900자에서 가장 높다(.518~.536).
- 말해주지 못하는 것: 충분 판정은 LLM 1회라 ±1~2문항이 노이즈이고, 조합 사이의 49~51 차이로 순위를 정할 수 없다. 같은 60문항에서 25개쯤 조합을 시험해 최고값을 골랐으므로 최고 점수는 실제보다 높게 나왔을 수 있다. 답변 품질(Faithfulness 등)과 입력 토큰 2배(1,523~1,549 → 약 2,900)의 지연·비용은 측정하지 않았다.
- 조건이 달랐던 점: hybrid_rerank의 리랭크 후보 수가 격자마다 다르다(`max(20, 2k)` / 22 고정). 400/10과 400/11처럼 k만 다른 값은 판정 노이즈를 포함한다.
- 방식 간 차이가 실험 효과인지 우연인지 확인한 방법: 같은 청크 목록의 판정은 캐시로 재사용했다. 같은 조합을 반복 판정해 흔들림을 재지는 않았다(미확인).

## 실패·이상 기록

아래 실행 오류와 중단은 이번 작업 세션의 실행 기록에서 옮겼고 원본 결과 파일에는 남아 있지 않다.

- 첫 `budget_sweep.py` 실행은 출력 버퍼링 때문에 진행이 안 보였고 CPU·GPU가 거의 쉬어 8분 뒤 중단했다. 같은 코드를 `python -u`로 다시 돌려 정상 완료했다(원인 확인 못 함).
- `budget_sweep2.py`의 첫 결과 표는 선정 결과 저장 키에 k가 빠져 같은 크기의 조합이 서로를 덮어썼다(400/8·10·11이 같은 값으로 나옴). 키에 k를 넣고 처음부터 다시 돌렸고, 이전 표는 `budget_sweep2_out_buggy.md`로 따로 보관했다. 이 문서는 수정 후 값만 쓴다.
- Advanced 첫 실행은 번호 정규식의 `\b`가 깨져(제어문자 → 글자 `b`) 1분 만에 중단하고 고쳐서 다시 돌렸다. 중단한 실행의 결과는 쓰지 않았다.
- Intermediate 첫 실행은 `chunking.CHUNK_OVERLAP_CHARS`를 지정하지 않아 즉시 오류가 났고 고쳐서 다시 돌렸다.
- 큰 격자는 `CUDA error: unknown error`로 한 번 실패했다. 직전에 프로세스를 강제 종료한 영향으로 추정하며, GPU 정상 확인 후 다시 돌려 완료했다(원인 미확정). 큰 격자 첫 시도(k 4~11, 크기 100~1000)는 중간에 직접 중단했고 조건(k 8~11, 크기 100~900)을 바꿔 다시 돌렸다.
- 큰 격자의 naive 검색 시간은 평균이 중앙값보다 훨씬 크다(예: 100자 평균 0.111초, 중앙값 0.019초, 최대 5.5초). 크기마다 임베딩 모델을 새로 불러 첫 질문에 로딩 시간이 섞였기 때문이다. naive 시간은 중앙값을 보아야 한다.
- 자동 채점 오류를 사람이 고친 경우, 검색 실패로 기록한 보류 문항, 모의 오류·`--mock` 제외: 없음.
