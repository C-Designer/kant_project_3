## 가설·배경

- 무엇이 문제였나: EXP-0014는 문맥 토큰 한도를 3000으로 고정해 돌렸고, 상위 k개의 토큰 합이 한도를 넘으면 그 청크와 **뒤 청크가 통째로 빠진다**(청크 본문을 자르지는 않는다). 어제 실행 재분석 결과 크기 100~900자 × 오버랩 0·10·20% × k 8~11 × 3방식 격자 19,440 사례(문항 60개) 중 2,050건(10.5%)에서 청크가 빠졌고, 그중 **근거 청크가 빠진 사례가 147건, 쪽+인용문 모든그룹이 깨진 사례가 57건**이었다. 확정값 900자는 hybrid_rerank k=11에서 60문항 중 58문항이 걸렸다. 그래서 EXP-0014의 큰 크기·큰 k 조합의 Recall은 한도 때문에 낮게 기록돼 있다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나: 문맥 한도를 3000 → 3400·3800·4200으로 늘리면 밀려났던 근거 청크가 돌아와 **Recall(쪽+인용문)이 오르고**, 입력 토큰과 지연 시간은 늘 것이다. 한도가 안 걸리는 조건은 3000과 **결과가 같아야 한다**(같으면 정상).
- 사전 예측(어제 토큰 합 분포, hybrid_rerank·오버랩 0%, 60문항 중 한도를 넘는 문항 수):

| 크기 / k | 3000 | 3400 | 3800 | 4200 |
|---|---|---|---|---|
| 600자 (k 5~11), 700자 (k 5~10), 800자 (k 5~9), 900자 (k 5~7) | 0 | 0 | 0 | 0 |
| 700 / 11 | 2 | 0 | 0 | 0 |
| 800 / 10 | 5 | 0 | 0 | 0 |
| 800 / 11 | 37 | 1 | 0 | 0 |
| 900 / 8 | 2 | 0 | 0 | 0 |
| 900 / 9 | 18 | 0 | 0 | 0 |
| 900 / 10 | 38 | 13 | 0 | 0 |
| 900 / 11 | 58 | 33 | 8 | 0 |

  즉 **한도 값이 결과를 바꾸는 조건은 900자 k≥8, 800자 k≥10뿐이고, 4200은 어느 조건에서도 안 걸려 "한도 없음"과 같다**고 예측한다. 이 예측과 다르면 "해석·한계"에 적는다.
- 지연 시간: EXP-0015에서 LLM 시간은 출력 토큰에 좌우됐고(r² 0.76) 입력 토큰과는 거의 무관했다(r² 0.01). 그래서 한도를 늘려 입력 토큰이 늘어도 지연 시간 증가는 작을 것이다.
- 좋아졌다고 판단할 기준 (**실행 전 초안, 확정 후 고치지 않는다**): 같은 (방식, 크기, k)에서 한도 X(3400·3800·4200)가 한도 3000과 비교해 **다음을 모두** 만족하면 "한도를 늘릴 가치 있음"으로 한다. 한도가 안 걸린 문항(문맥이 같은 문항)은 비교에서 빠지고 걸린 문항 수를 함께 적는다.
  1. Recall@k(page+quote, 그룹 단위)가 +.03 이상 높다(근거 있는 68문항에서 한 문항이 약 .015).
  2. 답변 행동 일치율이 .02 넘게 낮지 않다(72문항, 한 문항 약 .014).
  3. 전체 시간(같은 방식에서 검색 + LLM 답변 합계)이 한도 3000보다 1초 넘게 길지 않고, 입력 토큰 합계가 30% 넘게 늘지 않는다.
  4. RAGAS faithfulness가 .03 넘게 낮지 않다.

### AI 에이전트 실행 지침 (Claude Code, Codex 등. **이 절을 먼저, 끝까지 읽고 시작한다**)

**목표**: 이 문서의 담당 범위(k = 8)를 아래 명령으로 실행해 결과 파일을 만들고, 검증을 통과시키고, 이 문서의 "결과" 칸을 채우고, 사람이 읽을 보고를 남긴다. 4대 노트북의 결과를 나중에 **합쳐서 비교**하므로, **모든 노트북이 정확히 같은 환경·같은 조건으로 돌았다는 것이 무엇보다 중요하다.**

**환경 동일성 (가장 중요)**
- 환경 지문(`env_fingerprint`)은 `check` 단계에서 한 줄로 출력되고 `env.json`에 저장된다. 지문에는 파이썬·패키지 버전, `uv.lock`, torch·CUDA·NVIDIA 드라이버, **모델 판본(E5·리랭커의 HF 커밋 해시)**, **데이터(문서 PDF·골든 평가 파일) 지문**, **프롬프트 파일 지문**, 고정 설정값, 코드 커밋, 컴퓨팅 한도(스레드·코어·GPU 비율·병렬 수)가 들어 있다.
- **4대의 지문이 모두 같아야 한다.** 사람이 기준 지문을 알려주면 본 실행 명령에 `--expect-fingerprint <지문>`을 **추가**한다(다르면 시작 전에 멈춘다). 기준 지문이 없으면 첫 시험 실행의 지문을 사람에게 보고하고 다른 노트북과 대조해 달라고 요청한다.
- 지문이 다르면 `env.json`의 `identity`에서 **다른 항목을 찾아 기준 노트북에 맞춘다**(예: `uv sync`로 패키지를 `uv.lock`에 맞춤, `git pull`로 커밋 맞춤, 데이터 파일을 다시 받음). 맞출 수 없으면 **멈추고 사람에게 알린다.** 환경을 맞추지 않은 채 결과를 만들지 않는다.

- "좋아졌다고 판단할 기준" 1~4번을 각각 **충족 / 미충족 / 판단 불가**로 적고, 근거 숫자는 `merged.md` 표에서 인용한다(한도가 안 걸린 문항은 차이가 0이 정상이다).
- 문항 수가 적어 작은 차이는 우연일 수 있다고 적는다. 인과를 단정하지 않는다.
- 노트북 사이 환경이 다르다고 합친 표에 ⚠가 뜨면 반드시 "실패·이상 기록"에 적는다.

**최종 보고 형식** (사람에게 마지막에 이대로 남긴다)

### 지표 정의 (표에는 아래 이름을 그대로 쓴다)

Recall과 Hit를 **3단계로 따로** 적는다(뒤로 갈수록 엄격). 근거 있는 68문항 대상이다.

| 단계 | 뜻 | Recall | Hit |
|---|---|---|---|
| ① 문서(book_id) | 근거 문서의 청크를 가져왔는가(id만) | 공식 정의: 모든 그룹의 모든 대안 문서 중 찾은 비율 | 근거 문서를 하나라도 |
| ② 쪽(book_id+page) | 그 문서의 **근거 쪽** 청크까지 | 그룹 단위: 충족한 그룹 ÷ 전체 그룹(그룹 안 대안 하나면 충족) | 근거 쪽을 하나라도 |
| ③ 쪽+인용문(page+quote) | 그 쪽에서 **quote가 든 청크**까지(인용문 앞 40자, 공백·`|` 제거) | 그룹 단위 | quote가 든 청크를 하나라도 |

| 지표 | 정의 |
|---|---|
| 모든그룹 충족률 ①②③ | 모든 그룹이 충족인 문항의 비율(각 단계별) |
| 검색 시간 | `retrieve(질문, 방식, 11)` 호출 시작부터 청크 목록이 돌아올 때까지. 내부 단계(질문 임베딩+벡터 검색 / BM25 / RRF / 리랭크)도 따로 적는다 |
| 전체 시간 | 방식마다 `retrieve()`(직렬) + 문맥 조립 + LLM 답변(동시 8개 호출 중 한 호출의 시간)의 합. **검색, LLM 답변, 합계를 따로** 평균·중앙값·p95로 적는다. 동시 호출 수 8은 시험(같은 호출 18개를 1·4·8·16·24개로 보냄)에서 호출당 시간이 늘지 않은 값이며 총 시간이 약 6.6배 줄었다. 단독 호출(직렬) 시간은 공통 기준점으로 따로 본다 |
| 토큰 | 답변의 입력·출력 토큰(재생성 포함)과 faithfulness 채점 LLM의 입력·출력 토큰을 **따로** 센다 |
| faithfulness | RAGAS `faithfulness`(`src/judge/ragas_eval`의 보류 문장 제외 규칙), 3회 평균 |

Recall·Hit의 계산 방법(공식, 그룹 단위, 코드, 실제 예)은 `scripts/experiments/search/RECALL_EXPLAINED.md`에 쉬운 말로 정리돼 있다. 한도 때문에 **밀려난 청크는 못 찾은 것으로 센다**(LLM이 못 보기 때문).

### 실행 순서 (사람·AI 공통, 위에서부터 그대로)

**0. 준비** — 저장소 최신(`git pull`), `data/shipping/`(데이터는 별도 전달), `.env`(`OPENAI_API_KEY`, `OPENAI_BASE_URL`), `uv` 설치. 노트북은 **전원 연결 + 전원 모드 최고 성능**, 다른 GPU 작업 종료. 자세한 준비물과 문제 해결은 `scripts/experiments/search/README.md`.

**1. 시험 실행(몇 분)** — 환경이 맞는지 확인한다. 결과는 문서에 쓰지 않는다.
```bash
uv run python scripts/experiments/search/grid_kset.py --k 8 --k-order desc --sizes 900 --pcts 0 \
  --context-max 3000,4200 --ragas-sizes 900 --e2e-modes naive,hybrid,hybrid_rerank --e2e-workers 8 --limit-q 1 --out results/smoke
```
`DONE`이 나오고 `results/smoke/`에 `env.json`, `usage.json`, `questions.json`, `retrieval/`, `answers/`, `e2e/`, `ragas/`가 생기면 통과.

**2. 본 실행**
```bash
uv run python scripts/experiments/search/grid_kset.py --k 8 --k-order desc \
  --sizes 600,700,800,900 --pcts 0 --context-max 3000,3400,3800,4200 \
  --ragas-sizes 600,700,800,900 --e2e-modes naive,hybrid,hybrid_rerank --e2e-workers 8 --out results/exp0023/laptop4
```
기준 환경 지문을 받았다면 명령 끝에 `--expect-fingerprint <지문>`을 **추가**한다(다르면 시작 전에 멈춘다). GPU용 torch와 모델이 없으면 스스로 설치·내려받는다. 끊겨도(인터넷, 429) **같은 명령을 다시 실행**하면 끝난 설정은 건너뛰고 이어서 한다(코드를 바꿨다면 결과 폴더를 지우고 다시 실행).

| 단계 | 하는 일 | LLM | 규모 | 시간(추정) |
|---|---|---|---|---|
| check | 환경 점검, 모델 설치, GPU 메모리 점검 | 없음 | - | 약 1분 |
| retrieval | 색인, 선별 과정 기록, Hit·Recall(book_id, page+quote), 한도별 사용 청크 | 없음 | 크기 4 × 방식 3 × 72문항 | 약 22분 |
| answers | 답변 생성(병렬), 행동 일치율, 토큰. **문맥이 같은 한도는 답변을 재사용** | 있음 | 크기 4 × 방식 3 × k 1개 × 72문항 × 한도(재사용 후 새 호출만) + 확정값 | 약 11분 |
| e2e | 전체 시간(**검색 + LLM 답변**)을 **3방식 모두**. **검색은 직렬, LLM 호출은 동시 8개**(공통 기준점은 직렬). 큰 한도는 전 문항, 나머지는 문맥이 달라진 문항만 다시 호출 + 공통 기준점(시작·끝) | 있음 | 크기 4 × 방식 3 × k 1개 × 72문항 | 약 50분 |
| ragas | faithfulness(3회 평균, 채점 토큰 기록), 문맥이 같으면 한 번만 채점 | 있음 | 크기 4 × 방식 3 × k 1개 × 36문항 + 확정값 | 약 42분 |

합계 약 **2.1시간**(시험 실행에서 외삽한 추정. 실제 값은 `usage.json`의 단계별 `elapsed_s`로 기입). 비용은 단가를 몰라 `확인 불가`.

**3. 검증** — 결과가 끝까지, 같은 조건으로 만들어졌는지 확인한다(파일 개수, 레코드 수, 오류율, 토큰·faithfulness 누락, GPU·코어·환경). **통과해야 다음으로 간다.**
```bash
uv run python scripts/experiments/search/verify_results.py --in results/exp0023/laptop4 --k 8 \
  --sizes 600,700,800,900 --pcts 0 --context-max 3000,3400,3800,4200 --ragas-sizes 600,700,800,900 --e2e-modes naive,hybrid,hybrid_rerank --e2e-workers 8
```
`✅`는 통과, `⚠`는 진행하되 "실패·이상 기록"에 적는다, `❌`는 그 단계를 같은 명령으로 다시 실행한다. 마지막 줄이 `판정: **통과**`여야 한다.

**4. 결과 채우기** — 이 문서의 "결과" 칸을 표로 채운다(상태가 `실행 중`이 된다).
```bash
uv run python scripts/experiments/search/merge_grid_results.py \
  --in results/exp0023/laptop4 --doc docs/experiments/search/0023-ctxmax-k-8.md
```
같은 표가 `results/exp0023/laptop4/report/merged.md`에도 저장된다.

**5. 사례 보고서 만들기** — 문항마다 질문, 선별 과정, k개 청크 전문, 골든 quote·골든 답변, 최종 LLM 답변 비교, faithfulness가 담긴 파일이다. 한도 때문에 청크가 밀려난 문항만 따로 보려면 `--only-dropped`.
```bash
uv run python scripts/experiments/search/make_case_report.py --in results/exp0023/laptop4 --all
uv run python scripts/experiments/search/make_case_report.py --in results/exp0023/laptop4 --mode hybrid_rerank --size 900 --k 8 --only-dropped
```
**질문별로 파일을 분리해서** 한 문항씩 보려면 다음을 실행한다(확정값 900자·k=5는 모든 담당 폴더에 있다. 다른 크기·k는 `--size`·`--k`를 바꾼다). GPU·LLM은 필요 없다. 파일 하나에 다음이 들어 있다.

  - **질문 ↔ 골든 데이터셋 매핑**: 질문 파일과 골든 파일에서의 순번, 질문 글 일치 여부
  - 골든 기대(book_id·page·quote)와 **원본 쪽 텍스트**(접는 블록, quote 노란 표시), 골든 → 청크 매핑
  - **한도별로 밀려나는 청크**: 상위 k개 전부를 순위·토큰·누적 토큰과 함께 한도마다 ✅/❌로 표시(첫 청크가 한도보다 커서 잘려 들어가는 경우는 ✂로 표시)
  - 가져온 청크 본문 전문과 메타데이터(chunk_id, book_id, file_name, page, 점수, 순위, 원본 쪽 안 위치)
  - 놓친 근거 청크, 최종 LLM 답변과 골든 답변
```bash
uv run python scripts/experiments/search/export_question_md.py --in results/exp0023/laptop4 --mode hybrid_rerank --size 900 --k 5
```
`index.md`에 질문 목록·판정 요약·한도별 밀려난 청크 수가, `questions/`에 질문별 파일이, `source_pages/`에 원본 쪽 `.md`가 생긴다. 위 "결과 폴더 구조"의 `report/` 안에 저장된다.

`results/`(원자료와 `report/`)는 저장소에 올리지 않는다. 문서에는 대표 사례만 옮긴다.

**6. 마무리** — "해석·한계", "결정·후속 작업", "실패·이상 기록"을 쓰고(표를 보고 판단, 숫자를 만들어 쓰지 않는다), `- 담당 노트북:`과 `git_commit`을 채우고, 상태를 `완료`로 바꾸고, `docs/experiments/README.md`의 이 문서 행(상태·결정)을 갱신한다. push·PR은 사람이 시킬 때만 한다.
