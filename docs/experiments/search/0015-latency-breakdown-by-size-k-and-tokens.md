# EXP-0015. 청크 크기·k에 따른 검색 시간(내부 단계 포함)과 답변 LLM 시간의 요인(토큰, 문항 유형)을 분해한다

- 상태: 완료
- 날짜: 2026-11-12
- 작성자: @yshzjq
- run_id: 없음 (탐색용 분석 스크립트로 측정, 공식 metrics run이 아님)
- 관련: EXP-0014(답변 수집 데이터를 다시 분석), EXP-0013·EXP-0011(검색 격자), spec `docs/specs/search.md`, 스크립트 `search-notes/subsel_ia/retrieval_latency_detail.py`·`latency_extra_analysis.py`(저장소 밖 로컬)

> 값은 `metrics`의 RunRecord 흐름이 아니라 분석 스크립트로 잰 **탐색용 값**이다. 이 문서는 EXP-0014의 latency를 보완한다. EXP-0014는 검색 시간을 k=11 하나로만 쟀고, 답변 LLM 시간이 무엇에 좌우되는지 나누지 않았다.

## 가설·배경

- 무엇이 문제였나: EXP-0014 표의 "검색 + 답변 LLM = 합계"는 (1) 검색 시간을 k=11 한 번으로 모든 k에 적용했고 (2) 답변 LLM 시간을 24병렬 호출 중에 쟀고 (3) 시간이 청크 크기·k·답변 길이 중 무엇에 좌우되는지 나누지 않았고 (4) naive의 오버랩 0% 평균에 질문 임베딩 모델 로딩 시간(첫 질문 약 4초)이 섞여 있었다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나: 검색 시간을 k별·크기별·내부 단계별로 직접 재고, 답변 LLM 시간을 토큰·문항 유형별로 나누면 시간이 어디서 생기는지 알 수 있다. 사용자는 k를 늘리면 LLM 시간도 늘 것이라고 보았다.
- 좋아졌다고 판단할 기준: 사전 기준 없음(사후 정리).

#### 2. 입력·출력 토큰과 LLM 시간 (최소제곱 직선)

- 두 변수: `LLM 시간(초) ≈ 0.93 + 0.01 × 입력 토큰/1000 + 10.54 × 출력 토큰/1000` (r² = 0.764, 레코드 18,711개)
- 입력 토큰만: `6.10 + -0.33 × 입력/1000` (r² = 0.008). 출력 토큰만: `0.97 + 10.54 × 출력/1000` (r² = 0.764)
- 해석: 입력 1,000토큰이 늘면 LLM 시간이 약 0.01초, 출력 1,000토큰이 늘면 약 10.54초 늘어나는 직선이다. r²가 낮으면 토큰 수 외의 요인(서버 부하, 답변 내용)이 크다는 뜻이다.

#### 3. 재생성 추정

- 재생성(출력 형식 오류로 같은 질문을 한 번 더 호출)은 호출 수를 기록하지 않았다. 대신 입력 토큰이 청크 토큰으로 예상한 값의 1.6배를 넘는 레코드(같은 입력을 두 번 보낸 흔적)를 재생성 추정으로 센다: **13개 / 18,711개 (0.07%)**.
- 추정 방법의 한계: 직선(입력 ≈ 845 + 1.12 × 청크 토큰)에서 벗어난 정도만 본 것이라 오류 레코드(재생성에도 실패해 `error`가 남은 9건)는 빠졌고, 호출 횟수를 직접 센 값이 아니다.
- 추정된 레코드의 LLM 시간 평균은 4.82초(나머지 5.13초).

비용은 단가를 몰라 `확인 불가`. 오류율은 EXP-0014와 같다(18,720개 중 9건).

## 해석·한계

- 결과가 말해주는 것:
  1. **k는 검색 시간에 영향이 없다.** 모든 크기·방식에서 k를 바꿔도 평균 시간 차이가 naive 0.4ms, hybrid 1.0ms, hybrid_rerank 3.5ms 이하이고 k가 커져도 단조롭게 늘지 않으며, 900자 별도 측정(k 5~11)도 0.3ms 이하다. 하는 일이 k와 무관하기 때문이다(후보 수·POOL이 고정이고 k는 마지막에 자르는 개수만 바꾼다).
  2. **청크 크기의 영향은 방식마다 반대 방향이다.** naive·hybrid는 청크가 작을수록 느리다(100자 naive 19.0ms·hybrid 53.5ms, 300자 이상은 7.5ms·14.2ms 이하). 청크가 8,901개로 많아 BM25가 31ms까지 늘기 때문으로 보인다. hybrid_rerank는 청크가 클수록 느리다(100자 253ms, 900자 874ms). 리랭크가 합계의 80%(100자)~98%(900자)이고 후보 청크가 길수록 리랭크 시간이 늘어난다(100자 203ms, 900자 860ms).
  3. **질문 임베딩은 5~10ms, RRF는 0.1ms 이하다.** 검색에서 시간을 쓰는 곳은 리랭크뿐이다(hybrid_rerank).
  4. **답변 LLM 시간은 입력 토큰이 아니라 출력 토큰(답변 길이)에 좌우된다.** 입력·출력 토큰 직선의 r²는 0.764이고 입력 토큰만으로는 0.008, 출력 토큰만으로는 0.764이다. 출력 1,000토큰당 약 10.5초이고 입력 1,000토큰당 약 0.01초다. 그래서 k나 청크 크기를 키워 입력 토큰이 늘어도 LLM 시간은 거의 그대로이고, 100자 청크에서 LLM 시간이 길어지는 것(7~8초)은 답변이 길어지기(출력 약 596토큰) 때문이다.
  5. **문항 유형에 따라 시간이 다르다.** 보류 문항(abstain)은 답이 짧아 LLM 시간이 3.36초이고 답변 문항은 5.38초다. LLM 시간은 꼬리가 길어(평균 5.13초, 중앙값 4.11초, p95 11.68초, 최대 58.79초) 평균만으로는 대표 시간이 되지 않는다.
  6. **latency 밖에서 함께 보인 것: 되묻기·보류 문항의 행동 일치율이 낮다.** 답변 .978에 비해 되묻기 .692, 보류 .624다(EXP-0014의 전체 평균 .914는 답변 문항이 80%라 끌어올린 값). 원인은 이번에 조사하지 않았다.
- 말해주지 못하는 것: 검색 시간은 60문항 평균 한 번의 측정이고 GPU·로컬 메모리 Qdrant 값이다(공용 Qdrant의 네트워크 시간, CPU 서버의 리랭크 시간은 모름). 답변 LLM 시간은 24병렬 호출 중 측정한 값이라 단독 호출 시간과 다를 수 있고, 병렬과 직렬의 차이는 재지 않았다. 입력 토큰의 영향이 거의 없다는 것도 이 병렬 값에서 나온 결과다. 재생성은 호출 횟수를 기록하지 않아 입력 토큰으로 추정했다(13개 / 18,711개).
- 조건이 달랐던 점이 결과에 준 영향: hybrid_rerank의 후보 22개(확정값 20)와 오버랩 0만 잰 점. 후보 수가 적으면 리랭크 시간이 줄어드므로 확정 방식(후보 20)에서는 시간이 조금 짧다(900자 별도 측정 762~780ms, 이 문서 표의 900자 874ms).
- 방식 간 차이가 실험 효과인지 우연인지 확인한 방법: 검색 시간은 질문마다 k 순서를 번갈아 재서 순서 효과를 줄였고 k 사이의 차이가 1~3.5ms이고 k가 커져도 단조롭게 늘지 않는 점으로 "k 무관"을 판단했다. 반복 측정은 하지 않았다.

## 실패·이상 기록

- EXP-0014의 naive 검색 시간(오버랩 0% 설정의 평균 0.077~0.088초)은 첫 질문에 질문 임베딩 모델 로딩 시간이 섞인 값이었다. 이번에는 모델을 먼저 불러 6.2~19.0ms로 나왔다.
- 이번 검색 시간은 `retrieve()`를 그대로 부른 것이 아니라 같은 내부 함수를 같은 순서로 불러 단계마다 시간을 찍은 값이다. 추적 호출이 빠져 EXP-0014의 값(예: hybrid 800자 17ms)보다 작게 나온 곳이 있다(이번 11.2ms). hybrid_rerank 800자는 EXP-0014 0.798초, 이번 793ms로 거의 같다.
- 재생성 추정은 입력 토큰이 청크 토큰으로 예상한 값의 1.6배를 넘는 레코드를 센 것이라 직접 센 값이 아니다. 오류 9건은 이 추정에서 빠졌다.
