## 가설·배경

- 무엇이 문제였나: 지금까지의 격자는 k 일부(5·8~11)와 오버랩 일부 조건뿐이어서 k 4~11 × 크기 100~900 × 오버랩 0·10·20% 전체 조합을 한 번에 재지 않았다. 확정값(900자, 오버랩 0, k=5)과 같은 조건으로 대조한 값이 충분하지 않았고, 질문은 개발용+additional 60문항이었으며 `expansion_validation` 12문항은 쓰지 않았다. "쪽+인용문" 지표가 모든 그룹을 찾은 문항 비율뿐이어서 그룹 단위 Recall이 없었고, 전체 시간은 두 평균의 합이며 LLM 시간이 24병렬 중 값이었다.
- 무엇을 바꾸면 무엇이 좋아질 것이라 보나: 크기·오버랩·k·방식을 전체 격자로 재면 Recall과 답변 행동이 가장 좋은 조합(최적점)을 찾을 수 있다. 이 문서는 k = 5, 10만 맡고, 4개 문서를 합치면 k 4~11 전체가 된다. 최적점이 확정값보다 뚜렷이 좋지 않으면 확정값을 유지한다.
- 좋아졌다고 판단할 기준 (**실행 전 초안, 확정 후 고치지 않는다**): 같은 방식에서 확정값(900자·오버랩 0·k=5)과 비교해 다음을 **모두** 만족하면 "후보"로 한다.
  1. Recall@k(book_id)와 Recall@k(page+quote)가 모두 +.03 이상 높다(근거 있는 68문항에서 한 문항이 약 .015, Recall .02·모든그룹 충족률 .03 이하의 차이는 동률).
  2. 답변 행동 일치율이 .02 넘게 낮지 않고, 되묻기·보류 유형의 일치율이 확정값보다 낮지 않다(72문항, 한 문항 약 .014, .03 이하는 노이즈).
  3. 전체 시간(검색~LLM 답변, 직렬 측정 설정에서)이 확정값보다 1초 넘게 길지 않다. 입력 토큰 합계가 확정값보다 50% 넘게 늘지 않는다.
  4. RAGAS faithfulness(채점 설정에서)가 확정값보다 .03 넘게 낮지 않다.

## 질문 선택·실행 명령

- 질문 목록: Basic 골든 데이터셋 3개 `data/shipping/evaluation/` — `development.json`(30문항, 근거 있는 28), `additional.json`(30, 근거 28), `expansion_validation.json`(12, 근거 12). 합계 72문항, Recall은 근거 그룹이 있는 68문항으로 계산한다. 유형은 답변 57, 되묻기 7, 보류 8. 세 세트를 합친 값과 세트별 값을 모두 적는다. 시드 없음(고정 목록). RAGAS는 부하 때문에 **각 세트에서 홀수 번째 문항(15 + 15 + 6 = 36문항)**만 쓴다.
- 정답·`expected_action`·근거(quote)는 검색과 답변 생성에 쓰지 않고 채점에만 쓴다: 예 / 아니오 (실행자 확인)

**이 담당이 하는 측정 (5단계, 순서대로)**

| 단계 | 내용 | 범위 | LLM | 규모 | 시간(추정) |
|---|---|---|---|---|---|
| 1 | 색인 + 검색 지표 + 검색 시간 | 27설정 × 3방식 × 72문항(k=11 한 번 검색, k=5, 10를 앞에서 자름) + 확정값 | 없음 | 검색 5,832번 + 색인 27번 | 약 40~60분 (이전 격자 실측: 27설정 26분, 임베딩 포함) |
| 2 | 답변 행동 일치율, 토큰 | 27설정 × 3방식 × k 5, 10 × 72문항 + 확정값(k=5, 3방식) | 병렬 24 | 답변 약 11,880번 (입력 약 36M, 출력 약 4.5M 토큰, **추정**) | 약 1.0시간 |
| 3 | 전체 시간(직렬) | 크기 {100, 200, …, 900 (9종 전부)} × 오버랩 0 × **hybrid_rerank** × k 5, 10 × 72문항 + 앵커(500자·0%·hybrid_rerank·k=10, 시작·끝 72문항씩) | 직렬 | 약 1,440번 | 약 2.4시간 |
| 4 | RAGAS faithfulness | 크기 {500, 900} × 오버랩 0 × 3방식 × k 5, 10 × 36문항 + 확정값(3방식) | 병렬 8 | 채점 540건 (3회 평균) | 약 0.4시간 |
| 5 | 문항별 상세 저장 | 질문, 최종 청크, 골든 quote, 답변, 토큰, 시간(모든 단계 결과) | - | - | - |

합계 약 **4.7시간**(추정)이다. 단계 3에서 naive·hybrid의 전체 시간은 "그 방식의 검색 시간 + 같은 (크기, k)의 hybrid_rerank LLM 시간"으로 합성해 표에 적는다(합성값임을 표시, LLM 시간은 방식이 아니라 답변 길이에 좌우된다는 EXP-0015 결과에 근거한다). 비용은 단가를 몰라 `확인 불가`.

지표 정의(표에는 아래 이름을 그대로 쓴다):

| 이름 | 정의 |
|---|---|
| Hit@k | 근거 문서(`book_id`)가 top-k에 하나라도 있으면 1 |
| **Recall@k (book_id)** | 찾은 근거 문서 수 / 전체 근거 문서 수 (공식 정의, 문서 단위) |
| **Recall@k (page+quote)** | 근거 그룹 중, 근거 **쪽**의 청크가 `quote` 앞 40자(공백·`|` 제거)를 담은 그룹의 비율 (그룹 단위 Recall) |
| 모든그룹 충족률 (page+quote) | 모든 그룹을 찾은 문항의 비율(EXP-0014의 "쪽+인용문 모든그룹") |
| 답변 행동 일치율 | 답변의 `status`(answered / needs_clarification / abstained)가 `expected_action`(answer / clarify / abstain)과 같은 비율. 전체와 유형별(답변·되묻기·보류) |
| 근거 문서 인용률 | 답변이 인용한 문서가 근거 문서를 포함하는 비율 |
| 토큰 | 입력, 출력, 합계. `llm.usage_scope()`가 합산한 API `usage_metadata`(재생성 포함) |
| 검색 시간 | `retrieve(질문, 방식, 11)` 호출 시작부터 청크 목록이 돌아올 때까지(`time.perf_counter`). 질문 임베딩 모델·리랭커·BM25는 크기마다 먼저 불러 로딩 시간을 뺀다. 평균·중앙값·p95 |
| **전체 시간** | `retrieve()` 시작부터 `chain.generate()` 반환까지를 **타이머 하나**로 잰 시간. 단계별로 ① 검색 ② 문맥 조립(`build_context`) ③ LLM 호출 ④ 후처리를 나눠 같이 기록한다. 평균·중앙값·p95 |
| RAGAS faithfulness | 프로젝트 `src/judge/ragas_eval`의 기록 LLM·보류 문장 제외 규칙으로 채점하고 `FAITHFULNESS_REPEATS`(3)번 평균. 다른 3개 지표(answer relevancy·context precision·context recall)는 이번에 재지 않는다 |
