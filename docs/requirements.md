## 한 줄 정의

- 분야·난이도: **해운 · Basic** (2026-11-05 확정. 15 PDF, 360쪽, 일반 질문 72개 + 보안 질문). Basic을 끝내고 여유가 있을 때만 Intermediate를 검토한다. 데이터 위치 `data/shipping/`.
- 여러 팀이 같은 분야·난이도를 골라도 된다. Basic을 골라도 최고 평가를 받을 수 있다.

## 필수 과제 4개

모두 팀 단위. 하나의 서비스에서 검색 방식을 바꿔 실행하면 된다.

1. **PDF 기반 RAG 서비스.** 질문의 대상과 조건에 맞는 근거를 찾아 답하고 **문서명과 페이지**를 표시한다. 조건이 빠졌으면 되묻고(needs_clarification), 자료가 없거나 문서 간 차이를 해결할 수 없으면 이유를 설명하고 보류한다(abstained). 적용 여부 판단은 LLM이 검색 결과와 프롬프트로 해도 된다. 별도 규칙 엔진이나 충돌 탐지 시스템은 필수가 아니다.
2. **세 가지 RAG 방식 비교.** Naive RAG, 하이브리드 검색, 하이브리드 + 리랭킹을 모두 구현해 같은 질문으로 비교한다. 결과를 보고 최종 방식을 고른다(Naive를 골라도 된다).
3. **FastAPI + LangChain + Langfuse.** 질문 → 검색 → 생성(gpt-6-luna) → 출처 표시를 한 요청으로 연결한다. 요청·응답을 검증하고 오류를 구분한다. **Langfuse 연동은 필수**: 질문, 검색 문서, 실제 모델 입출력을 같은 요청 ID로 묶는다. 시연은 FastAPI docs 화면으로 해도 된다.
4. **평가셋으로 품질 확인.** 팀이 고른 일반 질문 전체를 세 방식으로 실행하고 전부 평가한다. 검색 Hit@k·Recall@k, 답변 RAGAS Faithfulness + LLM-as-a-Judge(사실·조건·근거·판단), 운영 지표(응답 시간·오류율·입출력 토큰), 보안 답변 4개. 상세는 [evaluation.md](evaluation.md).

## 범위 밖 / 선택

- **선택:** 대화 메모리, 사용자 화면, 고급 RAG, 추가 평가 지표, 운영 지표 개선 실험, 비공개 테스트셋, 캐싱·권한·문서 갱신·도구 호출. 필수를 끝낸 뒤에만 한다.
- **범위 밖:** 파인튜닝, 별도 모델 비교, 클라우드 배포, OCR, 범용 계산 엔진, 실제 예약·메일·계정·장비 제어.
- 항목별 별도 보고서는 필요 없다. 비교표와 실행 기록에 정리한다.

## 데이터 규칙

- ZIP을 모두 **하나의 빈 폴더**에 푼다. 안에 `documents/`와 `evaluation/`이 있다.
- 검색 대상은 `documents/*.pdf` **전부**. 노션의 PDF 개수와 실제 파일 수를 대조하고, 빠진 문서와 처리 실패를 기록한다.
- `evaluation/` 의 질문·정답·채점 기준 JSON은 **색인하지 않고, 검색어·필터·생성 입력에도 넣지 않는다.** 답변을 만든 뒤 채점에만 쓴다.
- **`book_id` = PDF 파일명에서 `.pdf`를 뺀 값** (`FB01.pdf` → `FB01`). 파일명은 바꾸지 않는다. 코드에서 `file_id`를 쓰면 같은 값.
- **첫 페이지 = 1.** 여러 페이지를 합친 청크도 구절별 페이지를 남긴다.
- 없는 메타데이터를 만들지 않는다. 적용 조건은 원문에서 확인한다.
- 표는 행·열 제목, 단위, 각주를 함께 보존한다.
- 청크를 나눌 때 대상(장비·회사), 적용일, 단위, 출처가 떨어지지 않게 한다.

평가 파일 (`data/shipping/evaluation/`):

| 파일 | 내용 |
|---|---|
| `evaluation/development_questions.json`, `additional_questions.json` | 실행할 질문과 `id` |
| `evaluation/expansion_validation_questions.json` | Basic만. 확장 검증 질문 |
| `evaluation/development.json`, `additional.json`, (`expansion_validation.json`) | 참고 정답, `evidence_groups`, `expected_action`, 채점 기준 |
| `evaluation/security_questions.json`, `security_tasks.json` | 보안 질문·사례. Advanced는 `security_tasks.json`의 `question`만 사용 |

제공 문항 수: Basic 72개(개발 30, 추가 확인 30, 확장 검증 12), Intermediate·Advanced 각 60개(개발 30, 추가 확인 30). **필수 실행 수가 아니다.** 팀이 고른다.

## 청크 메타데이터

```json
{
  "page_content": "...",
  "metadata": {
    "book_id": "FB01",
    "file_name": "FB01.pdf",
    "page": 3,
    "chunk_id": "FB01-p3-c1"
  }
}
```

세 검색 방식은 **같은 PDF, 같은 청크, 같은 임베딩**을 쓴다. 검색 방식만 다르다.

## 검색 방식

| 방식 | 처리 |
|---|---|
| `naive` | 임베딩(dense) 유사도로 청크를 찾는다 |
| `hybrid` | dense + 키워드 검색 결과를 합쳐 순서를 정한다 |
| `hybrid_rerank` | 합친 후보를 리랭커로 질문과 다시 비교해 순서를 정한다 |

최종 문맥에 넣는 청크 수 `k`와 입력 토큰 한도는 세 방식에서 같게 둔다. 찾은 문서는 달라도 된다.

## API

경로와 필드 이름은 발제 예시이며 같은 정보를 담으면 바꿔도 된다. 아래를 우리 기본값으로 쓴다.

- `GET /health`: 응답 여부 확인.
- `POST /query`

요청:

```json
{ "question": "2026년 11월 2일 기준 장비 A의 자동 화면 꺼짐 시간은 몇 분인가요?", "retrieval_mode": "hybrid" }
```

빈 질문, 지원하지 않는 `retrieval_mode`는 **입력 검증 오류**(HTTP 4xx). 요청 ID는 서버가 만든다.

응답:

```json
{
  "request_id": "…",
  "status": "answered",
  "answer": "…",
  "reason": "…",
  "citations": [
    { "source_id": "S2", "book_id": "DEMO_NOTICE", "file_name": "DEMO_NOTICE.pdf", "page": 1 }
  ]
}
```

상태값:

| status | 뜻 | 누가 정하나 |
|---|---|---|
| `answered` | 근거가 충분해 답함. 정답 보증은 아님 | LLM |
| `needs_clarification` | 사용자가 알려 줄 조건이 빠짐. `answer`에 물을 내용 | LLM |
| `abstained` | 자료가 없거나 충돌을 해결할 근거가 없음. 양쪽 출처와 필요한 자료를 설명 | LLM |
| `error` | timeout, 재시도 한도 초과, 출력 검증 실패 등 시스템 오류. `reason`에 원인(`model_timeout` 등), `citations`는 빈 목록 | **코드** |

HTTP 상태(요청 처리 결과)와 답변의 정확성은 별개로 본다. 평가 파일의 `expected_action` `answer / clarify / abstain`은 각각 `answered / needs_clarification / abstained`에 대응한다.

## 프롬프트와 출력 검증

- 프롬프트는 **서비스 지시 / 질문 / 검색 자료**를 구분한다. 검색 청크에는 요청 안에서만 쓰는 자료 ID(`S1`, `S2`, …)를 붙이고, ID ↔ `book_id`·`file_name`·`page` 대응표는 **코드가 보관**한다.
- LLM 출력은 JSON 하나: `status`, `answer`, `reason`, `source_ids`. 문서명·페이지는 LLM이 만들지 않는다.
- 코드가 검증: 상태값, 필수 필드, `source_ids`가 문맥에 있던 ID인지. **문맥에 없던 ID가 나오면 정상 답변으로 통과시키지 않고** 출력 오류 처리하거나 정한 횟수 안에서 재생성한다.
- 검색 결과가 비면 "검색한 자료에서 확인하지 못했다"고 답하고 `source_ids`는 빈 목록. 세상에 자료가 없다고 단정하지 않는다.
- 날짜가 늦거나 검색 순위가 높다는 이유만으로 값을 고르지 않는다. 정정 공지가 **무엇을, 어느 대상에, 언제부터** 바꾸는지 확인한다.
- 문맥을 줄일 때도 대상, 적용일, 단위, 정정 내용, 출처는 남긴다.
- `timeout`, 최대 호출 수, 재시도 횟수는 **실행 전에** 정해 둔다.
- 조건이 빠진 질문은 사용자가 완성된 질문을 새로 보내면 된다(대화 메모리 불필요). 조건이 이미 명확하면 불필요하게 되묻지 않는다.

발제의 판단 순서 예시(프롬프트에 반영):

1. 질문의 대상, 기준일, 필요한 조건 확인
2. 검색 자료가 그 대상과 조건에 적용되는지 확인
3. 값이 다르면 정정 공지가 무엇을 바꾸는지 확인
4. 근거 충분 → `answered`, 조건 누락 → `needs_clarification`, 자료 없음·충돌 미해결 → `abstained`
5. 문서에 근거한 주장마다 자료 ID 연결. 없는 출처를 만들지 않음

## 실행 기록 (Langfuse 필수)

요청 ID로 묶어 남길 것: 질문 원문, 검색 결과, **실제 최종 문맥**, 실제 모델 입출력, 상태, 인용, 응답 시간, 입력·출력 토큰, 오류. JSONL은 보조 기록으로 써도 된다.

- 대표 요청 하나를 열어 "어떤 질문에 어떤 자료를 찾았고, 모델에 무엇을 넘겼고, 어떻게 답했는지" 따라갈 수 있어야 한다. 정정 공지를 **못 찾은 경우**와 **찾았지만 문맥을 줄이다 빠진 경우**를 구분할 수 있어야 한다.
- 측정하지 못한 값은 `null`로 두고 **0으로 바꾸지 않는다.**
- 오류가 나도 확인된 사용량과 오류 이유를 남긴다.
- API 키와 개인정보는 기록에 남기지 않는다.
- 평가(RAGAS·Judge) 호출의 시간·토큰은 서비스 호출과 구분한다.
- Langfuse 확인 방법은 README나 발표자료에 적는다.

## 금지 사항

- API 키와 개인정보를 저장소, 로그, 발표 화면에 남기지 않는다. 설정은 환경 변수로만.
- 정답·근거·기대 동작을 검색 자료나 답변 생성 입력에 넣지 않는다.
- 결과를 "비공개 테스트 성능"으로 소개하지 않는다(질문·정답이 공개돼 있음).
- 교육용 가상 자료를 실제 업무 근거로 쓰지 않는다.
- 좋은 결과만 골라 합치지 않는다. 실패, 오류, 확인하지 못한 부분도 결과에 남긴다.
