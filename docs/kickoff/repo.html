2. 문서 세 종류가 각각 정하는 것

쉽게 말하면: requirements·evaluation은 발제가 시킨 것, ADR은 우리가 왜 그렇게 하기로 했는지, spec은 내 영역이 지금 어떻게 동작하는지다. 코드는 spec을 따르고, 동작을 바꾸면 코드와 spec을 같은 PR에서 고친다.

담당자가 되면 제일 먼저 할 일은 자기 spec에서 "미정"이라고 적힌 칸을 실제 값으로 채우는 것이다. 그게 곧 팀에 공유되는 설계 문서다.

작업 전에 읽는 순서 (AGENTS.md)

  1. docs/branch-strategy.md — 브랜치·PR 규칙
  2. docs/requirements.md — 무엇을 만드나, 발제의 고정 규칙
  3. 자기 영역 docs/specs/<영역>.md + src/contracts.py
  4. 채점 관련 작업이면 docs/evaluation.md

에이전트(Claude Code, Codex)도 같은 순서다. CLAUDE.md가 1번과 문서 규약을 자동으로 끌어온다.

문서별로 언제 고치나

문서고치는 때
spec동작·구조를 바꾸는 PR마다, 같은 PR에서. 미정을 확정했을 때
ADR되돌리기 어려운 선택(스택, 데이터 구조, 인터페이스, 협업 규칙). 번호 = 마지막 + 1. 기존 ADR은 안 고침
README설치·실행, Langfuse 확인법, 최종 선택, 기여 — 제출 전 각자 자기 절
requirements / evaluation발제 원문과 다를 때만
work-plan담당·일정·운영 방식이 바뀔 때

3. 내 폴더에서 지킬 것

  • 영역 하나 = 담당 1명 = spec 1개 = src/<영역>/ 1개. 레이어가 아니라 "무엇의 품질을 책임지나"로 나눴다(ADR 0002).
  • 다른 영역 폴더는 읽되 고치지 않는다. 고쳐야 하면 담당자에게 Issue나 PR 코멘트로.
  • LLM 호출은 platform.llm.call()로만. 직접 SDK를 부르면 측정과 트레이스가 빠진다.
  • 동결 설정은 config.py에만. k, 토큰 한도, 모델, timeout을 코드에 흩뿌리지 않는다.
  • 테스트는 규칙을 고정하는 용도. None 집계, source_ids 검증, book_id 파생 같은 발제 규칙만. 커버리지 목표 없음.
  • 커밋 금지: data/, .env, 키, 개인정보.
