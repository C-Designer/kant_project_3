안건 3 · 5분

질문 하나는 어떻게 답이 되나?

입구(platform)가 질문을 받아 번호표를 붙이고, search가 조각을 찾고, answer가 그 조각만 보고 답을 쓰고, platform이 시간·토큰을 재서 Langfuse에 남긴다. 실험 러너도 같은 함수를 부른다.

  • 왜 한 길인가. API 응답과 실험 결과가 같은 코드를 지나야 비교가 공정하고, 측정 코드가 한 곳(run_query, llm.call)에만 있어도 된다.
  • LLM은 직접 부르지 않는다. platform.llm.call()을 통해야 timeout·재시도·토큰·기록이 붙는다.
  • 출처는 LLM이 만들지 않는다. LLM은 S1, S2 같은 자료 번호만 쓰고, 코드가 문서명·페이지로 바꾼다. 없는 번호가 나오면 다시 만들게 한다.

부록: 질문이 답이 되는 과정 · docs/specs/platform.md

안건 4 · 5분

세 방식은 어떻게 비교하나?

metrics가 고른 질문을 세 방식으로 돌려 결과를 한 줄씩 저장하고, judge가 정답과 대조해 점수를 매기고, metrics가 둘을 합쳐 표로 만든다. 정답 파일은 채점에만 쓴다.

무엇을 재나어떻게담당
검색이 정답 문서를 찾았나Hit@k(하나라도), Recall@k(몇 개나). 문서 단위, k는 세 방식 동일metrics
답이 찾은 자료에 근거했나RAGAS Faithfulness. 입력은 실제 최종 문맥judge
답이 맞나LLM Judge 4항목: 사실·조건·근거·판단 각 0/1. 해당 없음·평가 불가는 nulljudge
얼마나 걸리고 얼마나 쓰나응답 시간, 오류율, 입·출력 토큰. 채점 호출은 따로 센다platform 측정 · metrics 집계
공격 문장에 넘어가나최종 구성 1개 × 보안 질문 2개 × 기본/방어 프롬프트 = 답변 4개platform

부록: docs/evaluation.md · docs/specs/metrics.md, judge.md

안건 6 · 7분

일은 어떻게 받아서 어떻게 넣나?

할 일 하나 = Issue 하나. 바꾼 것 한 묶음 = PR 하나. main에 넣는 것은 리드만. 보드는 그 상태를 보여주는 창이다. 할 일은 Issue에 라벨(영역)·마일스톤(기한 묶음)·담당자가 붙어 있고, GitHub 마일스톤은 M1(11/6)·M3(11/10)·M6(11/13) 셋뿐이다. GitHub가 처음이면 아래 부록의 안내를 미팅 뒤에 꼭 읽는다.

Issue를 고른다

보드 상단 탭 "담당별"에서 내 이름 아래 카드. 본문에 할 일·완료 조건·기준 문서가 있다. 지금 내 Issue는 전부 M3(11/10까지) 아니면 M6(11/13까지).

최신 main에서 브랜치를 판다

git switch main && git pull → git switch -c feat/chunking

작업하고 커밋·push한다

git add <파일> → git commit -m "feat: 청킹 v1" → git push -u origin feat/chunking. 에이전트로 해도 되지만 내가 설명할 수 있는 코드만.

반나절 단위로 PR을 올린다

제목 feat: 청킹 v1, 본문은 템플릿: 무엇을 왜 / 실행 명령과 결과 캡처 / 체크 4개 / 맨 아래 Closes #13(이게 있어야 Issue와 연결된다). 올린 뒤 보드 탭 "보드"에서 카드를 Review 칸으로 드래그한다(또는 카드 클릭 → Status를 Review로).

리드가 보고 머지한다

보는 것 4가지: 돌아가나(증거), spec과 맞나, 키·데이터 없나, 내가 설명할 수 있나. 스타일은 안 본다. 수정 요청이 오면 같은 브랜치에 push.

머지 뒤 정리

원격 브랜치는 자동 삭제. 로컬은 git switch main && git pull && git branch -D feat/chunking

부록: GitHub가 처음이라면 (처음 한 번 설정, 용어, 어디서 보나, 명령 복붙, PR 본문 예시, 캡처 붙이기, 자주 하는 실수) · 일을 받아서 main에 넣는 순서 (규칙 전체, Issue 40개 표)

안건 8 · 10분

오늘 정할 것과 오늘 할 것

정하면 담당자가 자기 spec의 "미정"을 지우고 값을 적는다. 그 PR이 각자의 첫 PR이어도 좋다.

미팅에서 정한다

  • k 기본값 — 답 만들 때 쓰는 조각 수. 세 방식 공통 (search·answer·metrics 모두 영향)
  • 평가 LLM — 생성 모델과 같아도 됨. 비용이 질문 수를 정한다 (judge)
  • Langfuse Cloud vs 셀프호스트 — 팀 프로젝트 하나, 키는 각자 .env (platform)
  • Python 버전 · 패키지 도구 · Qdrant 실행 방식(docker/embedded) — 전원이 같은 환경. 11/12 재설치 검증 대상. 10분 안에 못 정하면 리드가 오늘 저녁 Slack에 설치 명령 공지 (platform)
  • 데이터 다운로드·PDF 15개 검수 당번 — 노션 수와 실제 파일 수 대조, 누락·실패 기록
  • 발표 목차 7장 합의 · 발표 시간 공지 확인 — ①문제·데이터 ②아키텍처 ③비교 결과 ④품질·보안 ⑤운영·선택 ⑥한계 ⑦기여. 시간 미공지면 누가 확인하나
